# 5\. Requirement Appendix

### **5.1 Business Rules**

| **ID** | **Rule Definition** |
| --- | --- |
| BR-AUTH-01 | Primary user authentication must be performed securely via GitHub OAuth2 Single Sign-On (SSO) with authorized read/write scopes |
| BR-AUTH-02 | Each user account is restricted to a single active JWT login session at a time; authenticating from a new device automatically invalidates existing active refresh tokens. |
| BR-AUTH-03 | Personal Access Tokens (PATs) generated for programmatic API integration must have a mandatory expiration period (default: 30 days) and enforce API rate limiting. |
| BR-RBAC-01 | Users can only access system functions, workspace repositories, and navigation menus authorized for their specific assigned RBAC Role (`DEV`, `STAFF`, `MGR`, `TL`, `ADMIN`). |
| BR-RBAC-02 | Creating a new workspace automatically assigns the creator as the Workspace Owner with full management privileges. |
| BR-RBAC-03 | Every workspace must maintain at least one active Workspace Owner (`TL` or `ADMIN`); removing the final owner from a workspace is strictly prohibited. |
| BR-WS-01 | Logical workspace boundaries must strictly segregate connected GitHub code repositories, documentation templates, and team member access at the database schema level. |
| BR-WS-02 | Workspace slug identifiers must be globally unique within the organization and conform to lowercase URL-friendly alphanumeric formats. |
| BR-REPO-01 | A GitHub repository can only be bound to one active workspace at a time to prevent conflicting AST indexing pipelines. |
| BR-REPO-02 | Connecting a GitHub repository requires valid GitHub App OAuth installation credentials and organization repository read/write authorization. |
| BR-HOOK-01 | All incoming GitHub Webhook event payloads must be validated using HMAC-SHA256 signature verification against stored secret signing tokens before processing. |
| BR-HOOK-02 | Automated Webhook subscriptions are restricted to `push`, `pull_request`, `release`, and `repository_dispatch` triggers for continuous code-doc synchronization. |
| BR-HOOK-03 | Disconnecting a repository from a workspace immediately revokes active webhooks and archives indexing metadata without purging historical audit logs. |
| BR-AST-01 | Automatic Abstract Syntax Tree (AST) parsing and code entity extraction are strictly limited to configured supported programming languages (Java, Python, TypeScript). |
| BR-AST-02 | Executing a codebase re-indexing job acquires a concurrent execution lock on the target repository to prevent race conditions during vector calculations. |
| BR-AST-03 | High-dimensional vector embeddings computed from parsed AST code nodes must be persisted into Qdrant VectorDB with multi-tenant schema isolation. |
| BR-AI-01 | Every AI-generated document draft or update suggestion must attach explicit grounding evidence links (source file path, code entity name, line numbers, commit SHA). |
| BR-AI-02 | Prompt injection attempts or generated text failing grounding evidence verification guardrails must be automatically flagged and rejected by the AI Orchestration Engine. |
| BR-AI-03 | Retrieval-Augmented Generation (RAG) context assembly must strictly respect assigned workspace token budgets and context window limits. |
| BR-OCR-01 | Multimodal visual asset processing strictly supports PNG, JPG, SVG, WebP, and PDF document formats under a maximum file size limit of 10MB. |
| BR-OCR-02 | Multimodal document processing explicitly excludes audio and video media files from visual parsing. |
| BR-OCR-03 | OCR visual asset extraction must convert architectural diagrams and flowcharts into syntactically valid, editable Mermaid.js diagram code blocks. |
| BR-DRIFT-01 | Documentation drift alerts must be classified into Referential, Signature, or Semantic categories with assigned severity scores (Low, Medium, High, Critical). |
| BR-DRIFT-02 | Critical severity documentation drift automatically triggers GitHub PR status check failures to warn or strictly block PR merging based on configured workspace policy. |
| BR-DRIFT-03 | Dismissing a documentation drift alert or flagging a false positive requires Technical Lead or Staff Reviewer authorization with a mandatory justification comment. |
| BR-GOV-01 | Direct, unmonitored repository commits or publishing by the AI Engine are strictly prohibited under all operational conditions. |
| BR-GOV-02 | All AI-generated or auto-updated documentation must pass through a 2-Tier Governed Review Workflow (Tier-1 Staff Review → Tier-2 Manager Approval) prior to publishing, unless explicitly configured for auto-apply by a Manager. |
| BR-GOV-03 | Tier-1 Staff Reviewers can approve and forward documentation drafts to Tier-2, or reject drafts back to the Developer author with section-level feedback notes. |
| BR-GOV-04 | Tier-2 Manager Approval grants final publishing authorization, executing automated `.md` file commits directly to GitHub or generating an automated Pull Request. |
| BR-GOV-05 | Approval responsibility can be delegated or reassigned to another Manager, provided the delegate holds active workspace permissions. |
| BR-AUDIT-01 | Every document modification, approval decision, or auto-publish event must be immutably logged in a tamper-evident audit trail attributed to the acting role (`AI`, `STAFF`, `MANAGER`, `DEV`). |
| BR-AUDIT-02 | Critical system data and historical audit logs are permanent and cannot be deleted or overwritten; obsolete records can only be transitioned to Inactive/Archived status. |
| BR-VER-01 | Document version rollbacks restore the documentation content to any previously logged version state while generating a new attributed version entry in the change log. |
| BR-TMPL-01 | Creating, editing, cloning, or deleting dynamic documentation templates and mapping AST code placeholders is restricted strictly to Technical Leads and Administrators. |
| BR-TMPL-02 | AI-generated documentation outputs must strictly conform to the structural layout, section headings, and constraints defined by the assigned active template. |
| BR-TMPL-03 | Deactivated or archived documentation templates are immediately hidden and cannot be selected for new AI documentation generation pipelines. |
| BR-METRIC-01 | Workspace documentation health, freshness scores, and coverage metrics are automatically recalculated daily via a system scheduled background job (Cronjob) at 02:00 UTC. |
| BR-INTEG-01 | Third-party integration API credentials (GitHub App Secrets, Jira API Tokens, Slack Webhook URLs) must be stored with AES-256 encryption at rest and managed exclusively by Administrators. |
| BR-CONFIG-01 | AI Engine processing parameters (LLM model selection, temperature, token budget limits, and confidence thresholds) can only be modified by Administrators. |
| BR-QUOTA-01 | Workspaces exceeding their assigned monthly LLM token budget will have background AI generation temporarily paused until token quotas are reset or upgraded. |
| BR-CICD-01 | Automated GitHub Actions status checks shall post a `Pass` state on Pull Requests if no Critical or High severity documentation drift is detected. |
| BR-CICD-02 | Configured PR Merge Block policies (`Warn Only` vs `Strict Block`) dynamically dictate whether GitHub PR merges are permitted upon unresolved Critical drift. |
| BR-SEARCH-01 | Hybrid RAG search queries executed in the Knowledge Base shall strictly return documentation chunks and code nodes belonging to repositories bound to the user's active workspace. |
| BR-AUTO-01 | Auto-updated documentation drafts triggered by commit/PR webhooks are assigned a status of `Pending Review` and cannot auto-commit without human sign-off unless explicitly configured for auto-apply by a Manager. |
| BR-SYS-01 | Temporary draft snapshots and unverified user invite tokens older than 30 days are automatically purged by scheduled system maintenance background jobs. |

### 5.2 Common Requirements

|  |  |  |
| --- | --- | --- |
| **Req. ID** | **Requirement Name** | **Description** |
| CR-01 | Data Validation | All mandatory fields (marked with `*`) in input forms (e.g., Workspace Name, Repository URL, Branch Name, Template Title) must be validated on both client-side and server-side. The system shall prevent form submission if required data is missing. |
| CR-02 | Data Format Validation | The system must enforce correct formats for specific data types:  - **Email:** Standard RFC 5322 email format (e.g., `user@domain.com`).   - **Repository URL:** Valid GitHub HTTPS/SSH repository URL format (e.g., `[https://github.com/org/repo.git](https://github.com/org/repo.git)`).   - **Date/Time:** ISO 8601 standard format (`YYYY-MM-DDTHH:mm:ssZ`) in UTC.   - **Commit SHA:** 40-character hexadecimal string or 7-character short SHA.   - **Workspace Slug:** Lowercase alphanumeric characters with hyphens (e.g., `analytics-bi-pipeline`). |
| CR-03 | Authorization & Session Control | Every API endpoint and UI route must verify a valid JWT session token and check appropriate Role/Permission boundaries (`DEV`, `STAFF`, `MGR`, `TL`, `ADMIN`) before granting access. Unauthorized access attempts must be logged to the audit system. |
| CR-04 | Audit Trail Logging | All critical operations (such as approving/rejecting drafts, committing changes to GitHub, modifying templates, reassigning roles, or unlinking repositories) must be automatically logged with full context (`Actor`, `Timestamp`, `Action`, `Target Entity`, `Old/New Values`). |
| CR-05 | Unique Identifier Generation | The system shall automatically generate unique, human-readable codes and UUIDs for key system entities (e.g., Workspace Slug `WS-xxx`, Draft ID `DFT-xxx`, Alert ID `ALT-xxx`, Audit Log ID `AUD-xxx`). |
| CR-06 | Error Handling & Masking | The system must display user-friendly error messages (e.g., "GitHub OAuth token expired", "AST parsing timeout", "LLM token limit reached") on the user interface instead of exposing raw system exceptions, stack traces, or internal database schemas. |
| CR-07 | Concurrency Control | The system must handle concurrent operations (e.g., two reviewers updating the same draft, or concurrent Webhook events triggering AST indexing on the same repository) using optimistic locking or distributed locks (Redis/Kafka) to prevent race conditions and data inconsistency. |
| CR-08 | Visual File & Asset Sanitization | For uploaded visual assets (architecture diagrams, flowcharts, PDFs), the system must validate supported file extensions (`.png`, `.jpg`, `.svg`, `.webp`, `.pdf`), enforce a maximum file size limit of 10MB, and sanitize filenames to prevent path traversal attacks. |
| CR-09 | Asynchronous Task Processing | Long-running background operations (such as AST codebase indexing, Vision OCR extraction, and batch documentation generation) must run asynchronously via background workers, displaying real-time execution status (`Pending`, `In Progress`, `Completed`, `Failed`) to the UI via SSE/WebSockets. |
| CR-10 | Soft Delete & Data Retention | Critical entities (Workspaces, Repositories, Approved Documentation, Audit Logs) must never be hard-deleted permanently from the database; they must be soft-deleted using status flags (`is_archived = true`, `status = INACTIVE`) to ensure historical auditability and compliance. |
