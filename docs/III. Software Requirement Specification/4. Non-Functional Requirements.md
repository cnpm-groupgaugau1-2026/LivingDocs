# 4\. Non\-Functional Requirements

### **4.1 External Interfaces**

- This section defines the interfaces between LivingDocs and external entities, ensuring seamless interaction for internal users, developer workflows, and connected third-party systems.

### **4.1.1 User Interfaces (UI)**

- **Web Application:** The primary interface for system roles (Developer, Staff Reviewer, Manager, Technical Lead, Administrator) is a responsive web application built with **Next.js** and **Tailwind CSS**. It must support modern standard web browsers (Google Chrome, Microsoft Edge, Mozilla Firefox, Apple Safari) and adapt seamlessly to desktop (minimum $1280 \\times 720$ resolution) and tablet screen resolutions.
- **Language & Accessibility:** The user interface shall provide bilingual accessibility in both **English** (default for engineering workflows) and **Vietnamese**.
- **Consistency & Dark Theme:** UI components (buttons, dark-mode color schemes, typography, interactive side-by-side diff viewers, and status badges) must remain strictly consistent across all modules (`SCR-01` to `SCR-13`) to reduce the learning curve for engineering teams.

### **4.1.2 Hardware Interfaces**

- **Client Devices:** The system operates via web browsers on standard desktop PCs, laptops, and tablet hardware; no specialized peripheral hardware is required.
- **Server Infrastructure:** The backend deployment utilizes standard cloud/container server hardware (AWS EC2 / Docker Compose) running high-performance multi-core x86\_64 or ARM64 architectures for parallel AST parsing and vector calculations.

### **4.1.3 Software Interfaces (APIs & Integrations)**

The system communicates with the following external software components and cloud APIs:

- **Version Control Platform (GitHub):**
    - **GitHub OAuth2 & SSO:** Interfaces with GitHub OAuth endpoints for secure Single Sign-On, role verification, and JWT session generation.
    - **GitHub REST & GraphQL APIs:** Programmatically manages repository contents, opens Pull Requests, posts automated status checks, and commits approved `.md` documentation files.
    - **GitHub Webhooks:** Receives real-time asynchronous HTTP POST payloads (`push`, `pull_request` events) signed with HMAC-SHA256 signatures for automated code change tracking.
- **External AI & Vector Services:**
    - **Large Language Models (OpenAI / Anthropic):** Connects via secure REST APIs to OpenAI (GPT-4o, Azure OpenAI Gateway) and Anthropic (Claude 3.5 Sonnet) for RAG context synthesis and documentation generation.
    - **Vision-LLM Engine:** Interfaces with Multimodal Vision APIs (GPT-4o Vision) for Optical Character Recognition (OCR) and structural extraction from uploaded architecture diagrams, flowcharts, and PDF files.
    - **Embedding API:** Calls OpenAI `text-embedding-3-large` APIs to generate 1536-dimensional vector representations for AST code nodes and documentation chunks.
- **Third-Party Collaboration Services:**
    - **Issue Tracking (Atlassian Jira):** Interfaces via Jira REST APIs to extract metadata (ticket IDs, issue summaries) for attaching grounding evidence to documentation drift alerts.
    - **Communication Services (Slack):** Interfaces with Slack Webhooks and Bot APIs to dispatch real-time notifications for Tier-1/Tier-2 review assignments and critical drift alerts.

### **4.1.4 Communication Interfaces**

- **HTTPS/TLS Encryption:** All client-to-server and server-to-external-API communications must be strictly encrypted using **HTTPS/TLS 1.3** protocols.
- **Asynchronous Webhooks:** The system exposes a public secure endpoint (`/api/v1/webhooks/github/receive`) utilizing HMAC-SHA256 verification to listen to external repository event triggers.
- **Real-Time Data Streaming:** Uses **Server-Sent Events (SSE)** and **WebSockets** for streaming AI Markdown token generation directly to the client canvas in real time.
- **Event Broker Streaming:** Internal microservices exchange asynchronous system events using **Apache Kafka** message queues.

### **4.2 Quality Attributes**

### 4.2.1 Maintainability

- **Modular Architecture:** The codebase must follow a microservice architecture with clear service boundaries and separation of concerns between the Web Frontend (Next.js), Core Backend Services (Java Spring Boot), and the AI Processing Engine (Python FastAPI).
- **Code Standard & Documentation:** Source code must comply with established coding standards (Checkstyle for Spring Boot, Flake8 for FastAPI, ESLint for Next.js) and be documented using OpenAPI 3.1/Swagger specifications and inline technical comments.
- **CI/CD Pipeline Integration:** Automated CI/CD pipelines must automatically build, test (maintaining at least 80% unit test code coverage), and deploy services to maintain high system maintainability.

### 4.2.2 Usability

- **Reviewer & Approver Interface (Staff & Manager):** The Web Application must be designed for high review efficiency, allowing Staff and Managers to inspect grounding evidence, compare visual side-by-side code-vs-doc diffs, and complete review actions with no more than three (3) interactions.
- **Developer & Technical Lead Interface:** The web application shall provide a responsive interface for desktop and tablet devices, offering intuitive Markdown editing, dynamic Mermaid.js diagram previews, real-time token streaming visualization, and clear workspace navigation.
- **Visual Status Indicators:** Documentation drift severity must be clearly indicated using standardized visual indicators (Low, Medium, High, Critical) across all dashboards.

### 4.2.3 Reliability

- **Availability:** The system shall maintain an overall operational availability of at least **99.5%** during normal operation.
- **Failure Isolation & Auto-Recovery:** Background processing failures shall not affect user-facing services. Failed AI jobs must automatically retry or be stored in a Dead Letter Queue (DLQ) for later recovery.
- **Auditability & Traceability:** Every documentation change must be traceable to the acting role (AI, Staff, or Manager), triggering commit or Pull Request, and timestamp in a tamper-evident change log, producing deterministic drift detection results for identical code changes.

### 4.2.4 Performance

- **Response Time:** Standard API response time for standard operations shall not exceed **2 seconds** under normal workload, and full-text documentation search shall return results within **1 second**.
- **Drift Detection SLA:** The system shall analyze documentation drift for a Pull Request within **2 minutes** for software repositories containing up to **100,000 lines of source code (LOC)**.
- **Concurrency:** The system must support concurrent processing of at least **20 Pull Requests** without significant performance degradation.

### 4.2.5 Design Constraints

- **Technology Stack:** The system must strictly adhere to the specified stack: **Java Spring Boot** (Backend), **Python FastAPI** (AI Engine), **Next.js/React** (Web Frontend), **PostgreSQL** (Database), **Redis** (Caching), and **Kafka** (Message Broker).
- **Human-in-the-Loop Governance:** Unmonitored direct commits to repositories by the AI Engine are strictly prohibited; all auto-updated documentation requires human review (Staff review and Manager approval) before publishing, unless explicitly configured for auto-apply by a Manager.
- **Scope Constraints:** Version 1.0 strictly targets **GitHub** as the primary source control platform. Multimodal processing covers architectural diagrams, images, and PDFs, but explicitly excludes audio and video media files.

### 4.2.6 Security

- **Encryption:** All communications shall be encrypted using **HTTPS/TLS**. Sensitive credentials (GitHub tokens, API keys, LLM keys) shall be securely stored using encrypted secrets.
- **Access Control:** The system must enforce strict Role-Based Access Control (RBAC) restricting access according to user roles (Developer, Staff, Manager, Technical Lead, Administrator).
- **Authentication:** User authentication shall use OAuth2 / OpenID Connect (OIDC) via GitHub Enterprise SSO with single-session enforcement.
