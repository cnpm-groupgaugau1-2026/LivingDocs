# System Design



### **1. System Design**

### 1.1 System Architecture

The overall system architecture of the **LivingDocs System** is illustrated below. The system follows an **Event-Driven Decoupled Microservices Model** utilizing RESTful APIs and SSE (Server-Sent Events) for communication between the frontend web applications, core governance backend, AI processing engine, and external integrations.

1. **UI Components**

- **Developer & Staff Reviewer (Web App):** Web application built with **Next.js**.
    - **Functionality:** Provides interactive workspaces for developers and staff reviewers to inspect documentation drift alerts, view side-by-side code vs. doc diffs, generate AI documentation drafts, perform Tier-1 reviews, and query the RAG knowledge base.
    - **Note:** Developers cannot directly approve final publishing to main branches; all AI-generated updates must pass through the configured review workflow.
- **Manager & Administrator (Web App):** The workspace administrator, technical lead, and manager use a web application built with **Next.js**.
    - **Functionality:** Comprehensive workspace management dashboard including Tier-2 final approval center, repository binding settings, webhook monitoring, dynamic template builder, team RBAC assignments, and token quota controls.
    - **Governance Features:** Includes management of **2-Tier Approval Workflows**, automated GitHub commit policies, false-positive alert dismissals, and tamper-evident audit logs.

1. **Core System (Server-side)**

- **Core Governance REST API (Spring Boot):** Acts as the central processing unit, handling workspace business logic, security authentication (GitHub OAuth2 / JWT), RBAC authorization, 2-Tier approval state transitions, and audit logging. It exposes RESTful endpoints for the client-side applications.
- **AI Orchestration Engine (Python FastAPI):** Specialized microservice dedicated to heavy computation tasks: Tree-sitter AST parsing, code-vs-doc drift detection, grounding evidence extraction (file path, line number, commit SHA), hybrid vector search, and multimodal diagram OCR.
- **Real-time Communication (Server-Sent Events / SSE):** Acts as an intermediary for streaming live LLM documentation generation, real-time drift alert notifications, and background AST indexing progress updates to the frontend.

1. **External Systems / Third-parties**

- **GitHub REST & GraphQL API:** Used for fetching repository source code, parsing AST diffs, automated pull request generation, and executing direct commits upon Manager approval.
- **OpenAI / Claude APIs:** State-of-the-art LLM providers used by the AI Engine for context-aware documentation generation and vision OCR.
- **Apache Kafka:** Asynchronous message broker handling high-throughput GitHub Webhook events and decouples background AST re-indexing jobs.
- **Docker:** Used for containerization to ensure consistent deployment environments across development, testing, and production.
- **Redis:** Used for caching frequently accessed data, managing JWT session states, and acquiring distributed locks during concurrent AST indexing.
- **Jira & Slack:** Used for pushing real-time documentation drift alerts and workflow notification digests to team channels.

1. **Database Layer**

- **PostgreSQL (+ pgvector):** Stores structured relational multi-tenant data including user profiles, workspace bindings, repository credentials, document drafts, approval tasks, audit logs, and high-dimensional vector embeddings for RAG retrieval.
- **Redis:** Used for caching session state, API token rate-limiting counters, and preventing race conditions during concurrent webhook event processing.

**1.1.1 Backend Architecture**

The backend follows a **layered architecture pattern** within the Core Governance Service (Spring Boot) coupled asynchronously via Kafka with the AI Engine (FastAPI) to ensure separation of concerns, high maintainability, and loose coupling.

- **Controller Layer:** The entry point for HTTP requests. It handles incoming REST API requests from the Next.js frontend, validates input DTO formats, enforces security contexts, and delegates processing to the Service Layer.
- **Service Layer (Business Logic):** Contains the core business rules of the application (e.g., verifying RBAC permissions, executing 2-Tier approval workflows, parsing webhook payloads, and triggering AST indexing jobs). It orchestrates data flow and performs validations before interacting with the database or dispatching Kafka events.
- **Repository Layer:** Acts as an abstraction layer over the data access logic. It communicates directly with PostgreSQL using Spring Data JPA/Hibernate to perform CRUD operations on multi-tenant entities.
- **Database (PostgreSQL + pgvector):** The persistent storage for application states, audit trails, and high-dimensional vector embeddings for RAG retrieval.

**1.1.2 Web Application Architecture**

The Web Application is built using **Next.js**, structured to handle routing, real-time data streaming (SSE), global state management, and API data fetching efficiently for both developers and workspace administrators.

- **App Routing:** Manages the navigation structure of the application, directing users to the appropriate pages (e.g., System Dashboard, Docs Drift Alerts, Review Workbench).
- **Higher Order (Providers):** Wraps the application to provide global functionalities such as Authentication context (Auth Provider), State Management, Theme configuration, and Toast notifications.
- **Pages (SSR/CSR):** Represents the specific views visible to the user. Next.js allows for both Server-Side Rendering (SSR) for performance optimization and Client-Side Rendering (CSR) for interactivity.
- **Data Layer:** Handles communication with the Backend API via HTTP requests (using Axios or Fetch) to retrieve or update data, as well as listening for Server-Sent Events (SSE) for real-time updates.
